## 一、项目概述

### 1.1 背景与目标

一期移动端已基于 UniApp + Vue 3 技术栈完成基础功能开发并上线，覆盖了首页仪表盘、数据录入、告警中心、报表查看、个人中心、扫码功能等核心模块。经过一期运行，业务方和一线用户提出了以下改进需求：

- **设备巡检需求**：一线巡检人员需要在移动端完成完整的巡检流程，包括任务接收、GPS定位、逐项检查、拍照上传、异常上报。
- **报表增强需求**：管理人员需要在移动端查看多维度报表、同比/环比数据，并能导出PDF/Excel文件。
- **消息中心需求**：用户需要集中查看告警通知、审批通知、系统公告，支持实时推送和已读/未读管理。
- **离线体验优化**：地下配电房等无信号场景下，离线功能需更加稳定可靠，支持数据冲突检测与合并。
- **个性化体验**：用户期望支持暗色模式切换，降低夜间使用时的视觉疲劳。
- **图片处理优化**：巡检和抄表场景下的拍照、压缩、上传、预览体验需要优化。

**二期核心目标**：
- 在一期基础上迭代增强，开发周期约8周
- 覆盖巡检人员80%的日常巡检场景
- 提升管理人员移动端报表查看与决策效率
- 优化离线场景下的数据录入与同步可靠性
- 建立实时消息推送体系

## 五、风险与应对

### 5.1 风险清单

| 风险编号 | 风险描述 | 发生概率 | 影响程度 | 风险等级 |
|----------|----------|----------|----------|----------|
| R1 | **巡检流程复杂度风险**：巡检模板动态化、巡检项类型多样，前端渲染和数据校验逻辑复杂，可能导致M1延期 | 高 | 高 | **高** |
| R2 | **GPS定位精度风险**：地下/室内场景GPS信号弱或无法定位，需降级策略 | 中 | 中 | **中** |
| R3 | **离线数据冲突风险**：多人同时巡检/录入同一设备数据，冲突检测与合并逻辑复杂 | 中 | 高 | **高** |
| R4 | **多端导出兼容风险**：jsPDF/SheetJS在H5端可用，但小程序/App端需后端生成，两套方案需保持格式一致 | 中 | 中 | **中** |
| R5 | **WebSocket稳定性风险**：弱网环境下WebSocket频繁断连重连，影响消息实时性 | 中 | 中 | **中** |
| R6 | **极光推送审核风险**：App端使用极光推送需集成SDK，Android/iOS两端适配工作量可能超预期 | 低 | 中 | **低** |
| R7 | **暗色模式适配工作量风险**：一期所有页面和组件均需适配暗色模式，涉及大量CSS调整，工时可能超预期 | 高 | 中 | **高** |
| R8 | **后端排期风险**：后端仅1人，需兼顾巡检/消息/导出等多模块开发，可能成为瓶颈 | 高 | 高 | **高** |
| R9 | **包体积膨胀风险**：二期新增jsPDF、SheetJS等依赖，可能导致H5/App包体积超出限制 | 中 | 中 | **中** |

### 5.2 应对措施

| 风险编号 | 应对措施 |
|----------|----------|
| R1 | **M1第一周聚焦核心流程**：先实现基础巡检模板（布尔+数值型），动态模板和复杂类型后续迭代；巡检执行页采用分步式设计，降低单页复杂度；M1前两天完成巡检数据模型评审 |
| R2 | **GPS降级策略**：定位失败时使用默认厂区坐标并标记为"定位不精确"；提示用户手动确认位置；巡检提交时记录定位状态（精确/粗略/默认）供后台审核 |
| R3 | **分阶段实现冲突处理**：M2先完成基础冲突检测（服务端时间戳对比），M3完善冲突解决UI和合并策略；采用"服务端优先"的保守策略作为默认方案，避免复杂合并逻辑 |
| R4 | **统一导出模板**：后端和前端使用相同的导出模板定义（JSON配置），确保格式一致；H5端优先使用前端导出（更快响应），小程序/App端走后端（更稳定） |
| R5 | **WebSocket容错机制**：断线指数退避重连（最大间隔30秒）；重连期间使用HTTP轮询（间隔60秒）作为降级方案；消息接收后立即存入本地，确保不丢失 |
| R6 | **极光推送简化方案**：先用WebSocket+HTTP轮询实现消息通知（全端覆盖），极光推送作为增强方案在App端叠加；M4后半段再集成极光SDK |
| R7 | **CSS变量全量迁移**：M5开始前完成一期所有硬编码色值迁移为CSS变量；先完成核心页面（首页、列表、表单），再处理次要页面；UI组件库（uView）自带暗色主题的可直接启用 |
| R8 | **后端接口前置开发**：M1开始前2天，后端先完成巡检数据表设计和基础接口骨架；前端Mock数据先行开发，减少等待后端的时间；后端接口优先级：巡检 > 消息 > 导出 > 收藏 |
| R9 | **条件编译按需引入**：jsPDF和SheetJS仅在H5端引入（`#ifdef H5`），不打包进小程序/App；小程序/App端导出走后端生成；Chart依赖采用按需引入，不引入完整ECharts |

## 六、项目规范

### 6.1 代码规范

- 使用Vue3 Composition API + `<script setup>` 语法
- 组件命名：大驼峰（如 `InspectionItem.vue`、`ImageUploader.vue`）
- API请求统一封装在 `api/` 目录，按模块拆分（`inspection.ts`、`message.ts`、`export.ts`）
- 页面路由按功能模块分组（`pages/inspection/`、`pages/message/` 等）
- 二期新增Store命名规范：`useMessageStore`、`useThemeStore`
- 二期新增Composable命名规范：`useInspection`、`useReport`、`useMessage`
- WebSocket管理器采用单例模式，全局唯一实例
- 所有异步操作使用 `async/await`，错误统一捕获
- 图片处理相关工具统一放在 `utils/image-*.ts`
- 主题相关CSS必须使用CSS变量，禁止硬编码色值

### 6.2 Git分支规范

| `main` | 稳定版本，仅用于发布 |

## 七、与一期衔接说明

### 7.1 代码衔接

| 衔接项 | 说明 |
|--------|------|
| 项目结构 | 二期在一期项目结构基础上新增目录和文件，不修改一期已有文件结构 |
| Store兼容 | 一期Store（user、app、alarm、sync）保持不变；二期新增Store（message、theme）独立运行；syncStore V2与V1共存，支持渐进迁移 |
| API兼容 | 一期API封装保持不变；二期新增API独立文件 |
| 组件复用 | 一期公共组件（StatCard、TrendChart、EmptyState等）可直接被二期页面引用 |
| 路由扩展 | pages.json中新增巡检、消息等页面路由，不影响一期页面路由 |

### 7.2 数据衔接

| 衔接项 | 说明 |
|--------|------|
| 用户体系 | 完全复用一期用户认证体系（JWT Token + Pinia userStore） |
| 设备数据 | 复用一期设备列表和设备树接口 |
| 告警数据 | 一期告警Store和告警页面保持不变，M4仅做功能增强 |
| 离线数据 | syncStore V2兼容V1队列格式，首次启动自动迁移 |
| 缓存数据 | 一期仪表盘缓存、设备树缓存等不受影响 |
