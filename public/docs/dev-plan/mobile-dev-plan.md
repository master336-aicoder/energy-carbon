## 一、项目概述

### 1.1 背景与目标

随着企业能源与碳排放管理场景的延伸，一线人员（能源管理员、巡检人员、碳管理专员）急需一套轻量级移动应用，实现随时随地的数据查看、告警处理、现场数据录入及扫码识别。移动端作为PC Web端的有效补充，聚焦高频轻量场景，提升业务响应效率。

**核心目标**：
- 覆盖一线人员日常80%的移动端使用场景
- 复用现有Spring Boot后端API，降低后端开发成本
- 一套代码同时输出H5、微信小程序、Android App
- 7周内完成开发并上线

### 1.2 技术方案

| 层级 | 技术选型 | 版本 | 说明 |
|------|----------|------|------|
| 跨端框架 | UniApp | 4.x | 基于Vue3语法，一套代码输出多端 |
| 前端框架 | Vue.js | 3.x | 组合式API（Composition API） |
| 构建工具 | Vite | 5.x | 快速构建与热更新 |
| UI组件库 | uView UI | 2.x | 专为UniApp设计的高质量UI库 |
| 状态管理 | Pinia | 2.x | Vue3官方推荐状态管理方案 |
| HTTP请求 | uni.request + 拦截器封装 | — | 统一请求/响应处理 |
| 图表库 | uCharts | 2.x | 跨端高性能图表，适配ECharts数据格式 |
| 扫码能力 | uni.scanCode API | — | 调用原生扫码能力 |
| 本地存储 | uni.storage + 本地SQLite | — | Token缓存、离线数据存储 |
| 后端API | Spring Boot | 2.7.18 | 复用现有后端服务，零后端改造 |

### 1.3 多端输出策略

| 端类型 | 优先级 | 应用场景 | 说明 |
|--------|--------|----------|------|
| H5 | P0 | 嵌入企业微信/钉钉/浏览器访问 | 免安装，快速触达 |
| 微信小程序 | P0 | 微信生态内使用 | 便于推广，用户门槛低 |
| Android App | P1 | 需要离线能力、原生扫码、推送的场景 | 本地打包，按需分发 |
| iOS App | P2 | 后续根据业务需求评估 | — |

## 二、里程碑计划

### 总体时间线（共7周）

```
第1周    第2-3周    第4-5周    第6周      第7周
[ M1 ]   [  M2   ]  [  M3   ]  [  M4  ]  [  M5  ]
环境搭建  首页+录入   告警+报表   个人中心   测试上线
UI设计    +扫码                  +离线优化
接口联调
```

### 里程碑明细

| 里程碑 | 周期 | 时间 | 核心交付物 | 验收标准 |
|--------|------|------|------------|----------|
| **M1** | 第1周 | Day 1-7 | 1. UniApp项目骨架搭建完成<br>2. UI设计稿（高保真原型）确认<br>3. 公共组件库（导航、卡片、表单）完成<br>4. 登录/认证接口联调通过<br>5. 后端API适配清单确认 | 1. 可在H5/小程序/App三端正常运行登录页<br>2. UI设计评审通过<br>3. 公共组件在Storybook（或等效方案）可预览 |
| **M2** | 第2-3周 | Day 8-21 | 1. 首页仪表盘（KPI卡片、趋势图）<br>2. 数据录入模块（指标录入、产量录入）<br>3. 扫码功能（设备扫码、二维码识别）<br>4. 数据列表与详情页 | 1. 首页核心KPI与PC端数据一致<br>2. 数据录入支持手动输入+批量导入<br>3. 扫码可识别设备编码并跳转详情 |
| **M3** | 第4-5周 | Day 22-35 | 1. 告警中心（告警列表、告警详情、告警处理）<br>2. 报表查看（能耗日报/月报/年报、节能量报表）<br>3. 报表图表渲染（uCharts适配） | 1. 告警实时推送（WebSocket/App推送）<br>2. 报表数据与PC端一致<br>3. 图表支持缩放与数据下钻 |
| **M4** | 第6周 | Day 36-42 | 1. 个人中心（用户信息、密码修改、关于）<br>2. 离线缓存机制（数据录入本地存储、弱网自动重试）<br>3. 性能优化（包体积压缩、图片懒加载、列表虚拟滚动）<br>4. 多端适配细节打磨 | 1. 离线状态下可完成数据录入，联网后自动同步<br>2. 首屏加载时间 < 2秒（4G网络）<br>3. 包体积（App）< 20MB |
| **M5** | 第7周 | Day 43-49 | 1. 全功能回归测试<br>2. Bug修复与稳定性提升<br>3. 小程序审核与发布<br>4. H5部署到Nginx生产环境<br>5. App打包与内测分发 | 1. 测试用例执行通过率 > 95%<br>2. 崩溃率 < 0.1%<br>3. 小程序通过审核上线<br>4. H5可正常访问 |

## 五、风险与应对

### 5.1 风险清单

| 风险编号 | 风险描述 | 发生概率 | 影响程度 | 风险等级 |
|----------|----------|----------|----------|----------|
| R1 | **多端兼容性风险**：同一套代码在H5/小程序/App三端表现不一致（如扫码、文件上传、图表渲染） | 高 | 高 | **高** |
| R2 | **后端API适配风险**：现有API返回数据字段过多或结构不适合移动端，需要后端改造 | 中 | 中 | **中** |
| R3 | **UI还原度风险**：移动端屏幕尺寸多样，复杂图表在小屏上的可读性差 | 中 | 中 | **中** |
| R4 | **离线同步风险**：离线数据同步逻辑复杂，可能出现数据冲突或丢失 | 中 | 高 | **高** |
| R5 | **小程序审核风险**：小程序上线需微信审核，可能因类目、内容等问题被驳回 | 中 | 中 | **中** |
| R6 | **人员风险**：2名前端开发人员中有人请假或离职，导致进度延迟 | 低 | 高 | **中** |
| R7 | **性能风险**：App包体积过大或首屏加载过慢，影响用户体验 | 中 | 中 | **中** |

### 5.2 应对措施

| 风险编号 | 应对措施 |
|----------|----------|
| R1 | **M1阶段预留充分时间进行多端联调**；使用UniApp条件编译（`#ifdef H5/MP-WEIXIN/APP`）处理平台差异；建立多端测试矩阵，每次迭代至少覆盖2个端 |
| R2 | **M1阶段完成API适配清单评审**；优先使用现有API，前端做数据转换层；确实需要后端改造的，由后端人员每周集中处理 |
| R3 | **设计阶段以375px（iPhone标准宽度）为基准**；复杂图表在移动端改为简化版（如趋势图只保留1-2条曲线）；关键数据优先用文字卡片展示 |
| R4 | **采用简化版离线策略**：仅支持数据录入类表单的本地缓存，不做全量离线；每个缓存数据生成唯一UUID，同步时按时间戳覆盖；M4预留充分测试时间 |
| R5 | **M4提前准备小程序审核材料**（企业资质、ICP备案、服务类目）；提审前进行自审（使用微信官方审核规范检查）；准备备用上线方案（如先上H5） |
| R6 | **关键代码走查与文档沉淀**：M1-M2完成核心框架和组件封装，降低人员依赖风险；建立每日站会机制，及时发现进度偏差 |
| R7 | **采用分包加载策略**；图片资源使用CDN + WebP格式；uCharts按需引入组件；M4设置性能基线（首屏<2s，包体积<20MB） |

## 六、项目规范

### 6.1 代码规范

- 使用Vue3 Composition API + `<script setup>` 语法
- 组件命名：大驼峰（如 `AlarmList.vue`）
- API请求统一封装在 `services/` 目录，按模块拆分
- 页面路由按功能模块分组（`pages/home/`、`pages/alarm/`、`pages/report/` 等）
- 使用TypeScript进行类型约束（可选，根据团队熟练度决定）

### 6.2 Git分支规范

| 分支 | 说明 |
|------|------|
| `main` | 稳定版本，仅用于发布 |
| `develop` | 开发主分支 |
| `feature/M1-xxx` | 各里程碑功能分支 |
| `hotfix/xxx` | 线上紧急修复 |

### 6.3 提交规范

采用 Conventional Commits 规范：

```
feat(home): 添加首页KPI卡片组件
fix(alarm): 修复告警列表分页异常
docs(readme): 更新移动端开发说明
refactor(api): 优化请求拦截器逻辑
```
